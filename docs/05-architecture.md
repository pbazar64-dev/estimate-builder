# 05. Техническая архитектура

## 5.0. Исходное ограничение

Портал «Ава Тетис» — **облачный Битрикс24 (SaaS)**. Это означает:
- ❌ нельзя ставить локальные PHP-модули, свои таблицы в БД портала, править ядро D7;
- ✅ доступны: REST API, вебхуки/события, OAuth-приложения, встраивание через
  `placement` (iframe), Bitrix24 UI Kit (BX24.js).

Любое решение — это **внешнее приложение**, интегрированное по API. Вопрос лишь
в том, *где живут данные и логика* и *как строится UI*.

---

## 5.1. Сравнение архитектурных вариантов

### Вариант A. Нативные смарт-процессы (СП) Битрикс24
Данные — в СП/списках Битрикс24, UI — стандартные формы + бизнес-процессы.

| Критерий | Оценка |
|---|---|
| Сложность реализации | Низкая на старте, резко растёт на сложной логике |
| Производительность | Плохая на 1000+ строк (СП не рассчитаны на табличный редактор) |
| Масштабируемость | Ограничена лимитами облака и REST |
| Стоимость поддержки | Средняя, но «упирается в потолок» платформы |
| Интеграция с CRM | Отличная (нативная) |
| Сложный UI | ❌ Невозможно (формы СП не дают редактор смет, drag-and-drop, diff) |

**Вывод:** проваливает главное требование — профессиональный табличный UI и
мгновенный пересчёт больших смет. Не подходит как основной вариант.

### Вариант B. Внешнее приложение с собственным бэкендом (SPA + API)
Данные и логика — во внешнем сервисе (PostgreSQL + Node.js), UI — SPA,
встроенный в портал через `placement`. Битрикс24 — источник данных CRM и
идентичности.

| Критерий | Оценка |
|---|---|
| Сложность реализации | Средняя/высокая (свой сервис, но полный контроль) |
| Производительность | Отличная (свой бэкенд/БД, виртуализация таблицы) |
| Масштабируемость | Отличная (горизонтальное масштабирование, кэш) |
| Стоимость поддержки | Средняя (нужен хостинг), но предсказуемая |
| Интеграция с CRM | Хорошая (REST + вебхуки) |
| Сложный UI | ✅ Полный контроль (React, кастомный редактор) |

**Вывод:** закрывает все ключевые требования; цена — необходимость хостинга и
слоя интеграции с Битрикс24.

### Вариант C. Гибрид (СП как «витрина» + внешний редактор)
Смета-«карточка» и связь со сделкой — в СП Битрикс24 (для нативной интеграции и
прав), а тяжёлый редактор/версии/генерация — во внешнем сервисе; синхронизация
итогов обратно в СП.

| Критерий | Оценка |
|---|---|
| Сложность реализации | Высокая (две модели данных + синхронизация) |
| Производительность | Хорошая (тяжёлое — снаружи) |
| Масштабируемость | Хорошая |
| Стоимость поддержки | Высокая (двойная модель, риск рассинхрона) |
| Интеграция с CRM | Отличная |
| Сложный UI | ✅ Да (внешний редактор) |

**Вывод:** максимальная нативность, но дорогая поддержка и риск рассинхронизации
двух источников истины.

### Вариант D (доп.). Serverless-приложение на инфраструктуре Битрикс24
Хранение в СП/`entity`-хранилище + бессерверные обработчики. Снимает вопрос
хостинга, но наследует лимиты облака по объёму/скорости и не даёт полноценной
реляционной модели версий-слепков и аналитики. Годится максимум для лёгкого MVP,
не для целевой системы.

---

## 5.2. Рекомендация

### ✅ Вариант B — внешнее приложение (embedded SPA + собственный бэкенд)

**Почему:**
1. Единственный вариант, полноценно закрывающий требование «профессиональный
   редактор смет на 1000+ строк с мгновенным пересчётом, drag-and-drop, diff».
2. Собственная реляционная модель (PostgreSQL) идеально ложится на доменную
   модель (сметы, версии-слепки JSONB, каталог, страны, история согласования,
   аналитика) — без насилия над СП.
3. Полный контроль над генерацией DOCX/PDF и выгрузкой Excel.
4. Встраивание через `placement` даёт требуемое «открывается внутри портала».
5. Гибрид (C) добавляет нативности, но платит двойной моделью данных — на старте
   не оправдано; при желании нативную «витрину» в сделке можно добавить позже
   тонким слоем (виджет уже это делает).

**Что берём от Битрикс24:** идентичность (OAuth), данные CRM (сделка/компания/
контакт/реквизиты), уведомления и задачи для согласования, встраивание UI.

## 5.3. Технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Frontend | **React + TypeScript**, Vite | Кастомный редактор, экосистема |
| Таблица-редактор | AG Grid / TanStack Table + виртуализация | 1000+ строк, редактирование, drag |
| UI/стиль | Собственная дизайн-система «Vogue» (CSS) + BX24.js | Требуемый вид, встраивание |
| Backend | **Node.js + NestJS (TypeScript)** | Единый язык, модульность, DI |
| БД | **PostgreSQL** (+ JSONB для слепков версий) | Реляционность + гибкие снапшоты |
| Кэш/очереди | Redis + BullMQ | Кэш CRM-данных, фоновая генерация документов |
| Генерация DOCX | docxtemplater (шаблоны с переменными) | Кастомные шаблоны КП/договора |
| Генерация PDF | DOCX→PDF (LibreOffice headless) / Puppeteer для HTML-шаблонов | DOCX и PDF |
| Генерация Excel | ExcelJS | Формулы, группировки, форматирование |
| Интеграция B24 | REST API + вебхуки + OAuth 2.0 | Данные CRM, события, авторизация |

> Стек — рекомендация (заказчик указал «нет предпочтений»). Альтернатива на
> PHP (Laravel/Symfony) — ближе к экосистеме Битрикс24 и кадровому рынку
> интеграторов; при выборе PHP архитектура (слои, модель данных, API) остаётся
> идентичной, меняются лишь реализационные библиотеки.

## 5.4. Слои приложения

```
┌──────────────────────────────────────────────────────────────┐
│ Битрикс24 (облако): CRM, пользователи, задачи, уведомления     │
│  ▲ placement (iframe)         ▲ REST API / вебхуки / OAuth      │
└──┼───────────────────────────┼─────────────────────────────────┘
   │                           │
┌──┴───────────────────────────┴─────────────────────────────────┐
│ PRESENTATION (React SPA, встроен в портал)                      │
│  Реестр · Карточка · Конструктор · Diff · Каталог · Согласование│
│  Мастер · Настройки · Виджет сделки                             │
└──────────────────────────────┬──────────────────────────────────┘
                               │ REST/JSON (JWT сессии приложения)
┌──────────────────────────────┴──────────────────────────────────┐
│ BUSINESS LOGIC (NestJS)                                          │
│  EstimateService · VersioningService · CalcEngine ·             │
│  ApprovalService · DocGenService · CatalogService ·             │
│  RateService · AnalyticsService · B24IntegrationService ·       │
│  AuthZ (RBAC) · AuditService                                    │
└──────────────────────────────┬──────────────────────────────────┘
                               │
┌──────────────────────────────┴──────────────────────────────────┐
│ DATA ACCESS                                                      │
│  PostgreSQL (сметы, версии-слепки, каталог, страны, согласование,│
│  шаблоны, аудит) · Redis (кэш CRM, очереди генерации) ·          │
│  File storage (сгенерированные DOCX/PDF/XLSX, шаблоны)           │
└──────────────────────────────────────────────────────────────────┘
```

**Взаимодействие слоёв:** Presentation вызывает только REST API; вся бизнес-
логика и расчёты — на бэкенде (клиент дублирует CalcEngine лишь для мгновенного
UX, источник истины — сервер). Data Access скрыт за сервисами (репозитории).

## 5.5. Интеграционные точки с Битрикс24

| Точка | Механизм |
|---|---|
| Авторизация пользователя | OAuth 2.0 приложения (server-side), проверка `AUTH_ID`/`member_id` |
| Встраивание UI | `placement`: страница приложения + `CRM_DEAL_DETAIL_TAB` |
| Данные CRM | `crm.deal.get`, `crm.company.get`, `crm.contact.get`, `crm.requisite.*` |
| Согласование | `im.notify.*` (уведомления) + `tasks.task.add` (задачи согласующим) |
| Обновление сделки | запись статуса/суммы сметы в поля сделки (по требованию) |
| События | вебхуки `ONCRMDEALUPDATE` и т.п. для синхронизации |

## 5.6. Схема развёртывания

```
[Пользователь] → Битрикс24 портал (iframe placement)
                     │ HTTPS
                     ▼
        ┌─────────────────────────────┐
        │ Reverse proxy (nginx/TLS)   │
        └──────────────┬──────────────┘
             ┌──────────┴──────────┐
             ▼                     ▼
      [SPA static (CDN)]    [API (NestJS, N реплик)]
                                   │
                    ┌──────────────┼───────────────┐
                    ▼              ▼               ▼
              [PostgreSQL]     [Redis]     [Worker: docgen
               (+реплика)    (кэш/очереди)   LibreOffice/Excel]
                                   │
                                   ▼
                            [Object storage
                             (документы, шаблоны)]
```

- Контейнеризация (Docker) + оркестрация (docker-compose для стенда / k8s для
  прод при росте).
- Размещение — на выбор заказчика (VPS/облако РФ/ЕС); критично: доступность из
  портала и соответствие требованиям по данным (юрлица в РФ/РБ/КЗ/PL).
- Бэкапы PostgreSQL (PITR), хранение документов с версионированием.
